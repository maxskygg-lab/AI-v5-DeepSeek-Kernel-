# 后续发展规划（Roadmap）

> 基于当前实现状态（2026-11）编写。所有目标均为**规划口径**，非承诺交付时间；里程碑按依赖关系排序，
> 每个里程碑都有可验收的出口标准。

## 一、现状快照

**已具备**

- 主题级空间隔离（Pinecone namespace）+ 稳定工作区标识
- 混合检索：BM25 + Dense → RRF 融合 → Cross-Encoder 重排
- 多论文对比矩阵、溯源综述生成、跨论文覆盖策略
- 笔记云端持久化（独立 namespace、失败重试、刷新恢复）
- 学术检索：语义相关度与引用量权重可调、关系图谱、引用量补全
- Semantic Scholar 请求层：失败不写缓存、403 不做无意义重试、错误信息可读
- 大 namespace 分页取向量（按 URL 长度分组，规避 `414 Request-URI Too Large`）
- 图谱与论文卡片同位置渲染（聚焦论文自动展开）
- PDF 解析容错（PyMuPDF 回退）与空内容拦截

**结构性短板**

| 短板 | 现状 | 影响 |
|------|------|------|
| 单文件架构 | `app.py` 约 2270 行，UI / 检索 / 存储 / 解析耦合 | 改动风险高，无法并行开发 |
| 无评测体系 | 检索与生成质量靠主观感受 | 优化无法量化，回归无保障 |
| 无引用定位 | 只到论文级，不给页码/段落 | 学术场景可信度不足 |
| 同步阻塞 | 上传、解析、入库都在请求内完成 | 大 PDF 易超时，多用户并发差 |
| 无测试/CI | 仅本地手工验证 | 线上问题只能靠日志回溯 |
| 成本与配额不透明 | 无 token / 向量用量统计 | 免费额度耗尽才发现 |

## 二、对标分析

| 标杆 | 核心能力 | 对本项目的启示 |
|------|----------|----------------|
| **PaperQA2**（Future House） | 引用级溯源、矛盾检测、LitQA2 评测集 | 引用要精确到段落；质量必须用固定评测集衡量 |
| **SciSpace / ChatPDF** | PDF 对话、原文跳转、批注 | 答案旁给“跳到原文”入口，体验提升显著 |
| **Elicit** | 结构化抽取表、系统综述流程 | 把“对比矩阵”做成可复用模板与导出（CSV/RIS） |
| **Consensus** | 是/否证据聚合、结论强度 | 可增加“证据一致性”提示，避免单篇结论误导 |
| **NotebookLM** | 多文档 grounded 问答、来源面板 | 来源面板 + 一问多源引用，是可信度的关键 |
| **Research Rabbit / Semantic Scholar** | 引文网络、作者追踪、新论文提醒 | 图谱已有基础，可加“订阅主题 → 新论文推送” |
| **Zotero + Better BibTeX** | 文献管理与引用导出 | 补 BibTeX/RIS 导出，才能进入真实写作流程 |
| **RAGFlow / LlamaIndex** | 可配置切分、混合检索、评测工具链 | 切分参数与检索策略应可配置、可回归测试 |

**结论**：本项目在“检索 + 对比综述”上已接近同类产品的中上水平，主要差距不在功能创意，
而在**可信度（引用定位）**、**可度量（评测）**、**可维护（架构与测试）**三件事。

## 三、待优化点（按优先级）

### P0 · 稳定性与可维护性

1. `app.py` 拆分为 `services/`（检索、向量库、笔记、PDF 解析、LLM 调用）与 `ui/`（三个 Tab），入口只做编排
2. 建立 pytest 用例：namespace 生成、笔记读写合并、PDF 空内容拦截、混合检索排序
3. 接入 GitHub Actions：`black --check` + `pyflakes` + `pytest`
4. 结构化日志与错误上报（记录失败环节、耗时、namespace），替代 `except: pass`
5. 清理历史 namespace（约 3.5K 条重复数据），并加一次性的“存储体检”按钮

### P1 · 检索与生成质量

6. 构建 30–50 题的领域评测集（问题 + 期望证据段落），指标：Recall@5、MRR、引用命中率
7. 切分策略参数化（chunk_size / overlap / 按章节切分），用评测集选优，而非拍脑袋
8. 回答带页码与段落定位，前端提供“跳转原文”
9. Embedding 与 Reranker 升级评估（如 bge-m3 / bge-reranker-v2-m3），以评测集为准决定是否替换
10. 查询改写与多跳检索：先扩写同义词/术语，再检索；对综述类问题走多轮取证

### P2 · 体验与成本

11. 上传与入库异步化（后台任务 + 进度条），避免长请求超时
12. 扫描版 PDF 走 OCR（如 PaddleOCR / Tesseract）后再入库
13. 用量面板：token 消耗、向量条数、索引占用，配额预警
14. 笔记支持 Markdown 导出、按主题导出、批量删除

## 四、新增功能规划

**近期（M1–M2）**

- 引用跳转与来源面板（每条结论可点回原文位置）
- 对比矩阵模板化（方法/数据集/指标/结论四列可配置），支持导出 CSV
- BibTeX / RIS 导出，衔接 Zotero
- 主题订阅：按关键词或作者定时抓取新论文，站内提醒

**中期（M3）**

- 证据一致性提示：多篇结论冲突时显式标注（对标 Consensus / PaperQA2）
- 综述草稿工作区：大纲 → 分段生成 → 引用回填 → 导出 Word
- 多用户与权限：工作区成员、主题共享、只读链接

**远期（M4）**

- Agentic 深度研究：自动拆解问题 → 多轮检索 → 交叉验证 → 生成带引用报告
- 本地化部署选项（本地向量库 + 本地模型），满足数据合规
- 中英双语检索与跨语言综述

## 五、技术迭代路径

```
单文件 Streamlit
  → 模块化 + 单元测试 + CI                （M1）
  → 评测集驱动的检索调优 + 引用定位        （M2）
  → 异步任务队列 + 用量与可观测性          （M2 末）
  → 多用户与共享 + 综述工作区               （M3）
  → Agentic 检索与本地化部署选项            （M4）
```

关键决策点：

- **是否继续用 Pinecone**：数据量 < 10 万条且以单工作区为主时，可评估 pgvector / Qdrant 自托管以降本
- **是否换 Embedding**：必须先用评测集建立基线，再对比替换，避免“感觉更好”
- **是否拆前端**：Streamlit 满足课堂与小组使用；若走向多用户协作，再评估迁到 FastAPI + 前端框架

## 六、阶段性目标与验收标准

| 阶段 | 目标 | 验收标准 |
|------|------|----------|
| **M1 稳定收口** | 架构拆分、测试与 CI、历史数据清理 | `pytest` 全绿；CI 通过；线上无未捕获异常；旧 namespace 清空 |
| **M2 质量可度量** | 评测集 + 引用定位 + 检索调优 | 评测集 Recall@5 ≥ 0.8；答案引用可跳转原文；切分参数有对照结论 |
| **M3 产品化** | 异步化、导出、多用户 | 50 页 PDF 入库不超时；BibTeX/CSV 导出可用；主题可共享 |
| **M4 进阶** | Agentic 研究、本地化部署 | 复杂问题自动多轮取证并产出带引用报告；本地部署跑通 |

## 七、风险与边界

- **成本**：Cross-Encoder 与 LLM 调用是主要开销，需设配额与降级策略（超限退回向量检索）
- **并发**：Streamlit 单进程模型不适合重任务，异步化是前提
- **数据合规**：上传 PDF 的版权与隐私边界需在 UI 明示；本地化部署是长期解法
- **评测主观性**：评测集需固定版本并纳入仓库，否则优化无法比较
